# Local event delivery and engine isolation v1

createEventBus is an optional headless synchronous dispatcher for one activityId/sessionId/sourceId producer stream. It imports the pure Protocol bounded JSON copier, no engine, browser, framework, renderer or analytics transport. The host injects a trusted synchronous event validator (normally the optional validateEvent adapter). Validation must be side-effect-free. The bus binds all three identities and requires source sequence zero first, then contiguous safe integers. Engines inject source identity, clock and event UUID generation separately. It never derives global order from clocks.

## Admission, subscription and local ordering

publish copies and freezes input, validates it, checks identity/sequence/deduplication and queue capacity, then admits the event and increments the expected sequence. Rejections consume no sequence. Subscribers present at admission are captured in registration order. No implicit replay: subscribe defaults to future admissions only. Unsubscribe is idempotent and stops even captured callbacks that have not yet started; adding an observer during a callback does not receive that in-flight event unless explicitly replaying. Identical callbacks registered twice are independent subscriptions.

Delivery is synchronous when outside a flush. Reentrant publications enter a bounded FIFO rather than recursively calling observers; every surviving recipient of the current event finishes before the next event. A receipt says delivered only when its delivery task finished, or queued when waiting. The bus flushes at most maxPerFlush tasks per call and reports bus.yield if tasks remain. The host calls flush again at a deterministic scheduling boundary; no hidden timer or global microtask loop is installed. Async observers are not awaited; promise rejections are consumed and diagnosed. Async completion order has no effect on event/state order. Synchronous observers must finish promptly; JavaScript cannot preempt an arbitrary callback.

## Bounded memory, replay and pressure

Host options may only tighten ceilings: 128 pending tasks, 4 MiB pending encoded bytes, 128 retained history events, 4 MiB history bytes, 1,024 tasks per flush and 128 subscriptions. Each event is limited to 1 MiB, JSON depth 32, collection 1,000, string 4,000 and 10,000 values. Replay tasks consume the same pending count/byte limits. Replay registration rejects atomically if the retained tail cannot fit, before installing the subscription. History evicts oldest events by count/bytes; an individual event larger than its history byte cap is delivered without retention. History may be disabled.

Explicit replay delivers the retained admitted tail in admission order solely to the new observer, then future events. The tail can include admitted events still queued for older observers; admission-time recipient snapshots avoid double delivery to a new subscriber. Replay does not regenerate IDs, mutate engine state, re-evaluate or replay engine commands. No guarantee of a complete session log is made.

When queue pressure rejects admission with bus.backpressure, the caller retains the already-committed event in its own bounded outbox, reports overflow and retries the exact occurrence after flushing. Never silently retry with a different ID or roll back committed engine state. To avoid a committed transition with no event capacity, Core must reserve/preflight its transaction/outbox before commit. This bus cannot reserve engine state or fabricate a transaction guarantee; actual Core orchestration is its own issue. Stats expose queue/history/subscription sizes without event content.

## Failure isolation and deduplication

Observer exceptions and rejected promises report bus.subscriber and cannot escape publish or stop other observers. A failing diagnostic hook is also isolated; recursive diagnostic notification is suppressed. Diagnostics carry only safe codes, never callback exception text or event data. Immutable copies prevent an observer from mutating the shared event; engines must also avoid passing mutable state/engine handles into observers. Observer side effects outside this boundary remain the host's responsibility.

Inside the retained tail, an identical occurrence ID plus identical full JSON is bus.duplicate (no delivery); conflicting reuse is bus.conflict. Outside that finite window the contiguous source high-water sequence rejects old occurrences with bus.sequence. UUID reuse with a newer sequence outside the retained window cannot be detected forever with bounded memory: producers must never reuse IDs and remote sinks maintain their own retention/idempotency policy. Out-of-order/gapped events reject locally. A remote aggregator can archive/reorder multiple streams under an independently declared policy.

Local live delivery is one callback attempt per admitted task to each captured active subscription; intentional replay is another observation. Unsubscribe, disposal or process failure can interrupt delivery. This is neither durable nor exactly-once remote delivery. Remote retries, reconnect ordering, consent, redaction, persistence and idempotent export remain events#3.

## Exact emission points for engine integration

All success events follow committed transitions, never speculative state. created follows successful create; started follows the initial active transition; resumed follows validated successful restore. interacted follows an accepted action commit, with its action/revision. Domain-specific state events follow that same commit, then activity.interacted. attempt.started follows its creation; answer.changed/submitted and hint.requested follow accepted corresponding actions. On submission emit answer.submitted (when applicable), attempt.submitted, then activity.interacted. Completion emits activity.completed only once for the committed terminal revision after result validation, with matching IDs; pending evaluation emits no completion. Failed initialization/dispatch/evaluation/restore emits activity.failed with a safe code/phase after the failure outcome is committed; rejected actions have no success/domain events. Simulation events follow the named committed lifecycle/parameter changes; code.executed follows a finalized execution observation, never merely starting a job.

A transaction generating several events allocates contiguous sequences in that order and retains its bounded outbox. Failed subscribers do not reverse completion or trigger a second engine completion. Hosts cannot assume this standalone bus implements engine lifecycle rules: the docs specify integration obligations for subsequent Core/domain implementations. Replaying the observation of completion is allowed and must not complete the engine again.

dispose is idempotent: closes admissions, deactivates subscriptions, clears pending tasks/history/maps and releases diagnostic hooks. Disposal during a callback stops remaining callbacks; already running callbacks cannot be cancelled. Already returned queued receipts are not durable promises. Pending async observer code is host-owned; its eventual rejection is consumed without calling disposed hooks.

## Compatibility and checks

Existing event/Protocol wire schemas remain unchanged; the optional bus is a live host service, never serialized. npm test exercises multiple observers, exact order, reentrant admission, subscribe/unsubscribe during delivery, tail replay, bounded count/bytes, explicit flush, duplicate/conflict/stale rejection, observer throws during committed completion, async rejection, diagnostics isolation and cleanup. Existing JS/Python event fixtures and ES2022-only TypeScript consumers remain required. Concrete Core/browser/remote-sink conformance is not claimed here.
